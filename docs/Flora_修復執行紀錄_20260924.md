僅對這兩個服務新增 `healthcheck.disable: true`，解析後設定比對確認沒有其他差異；以原有 image、`--no-deps --pull never --no-build` 重建，於台灣 17:47:42 完成啟動。未重建 API、PostgreSQL、Redis 或前端。

## 2. 連線修復

封包採樣顯示原 Cloudflare 回源 TCP 握手／ACK 有數秒間隔，Nginx 收到請求後約 0.17 秒已開始回傳 HTTP 200。Windows→Cloudflare 自有 trace endpoint 約 0.14 秒，只有轉至 Flora 的路徑嚴重延遲。未發現主機 tc 人為延遲或 iptables mangle 規則。

已在使用者明確同意新增持續性連線後建立：

- Tunnel 名稱：`flora-hetzner`
- Tunnel ID：`95b30267-cd50-4838-bc90-311778c4e00d`
- 僅公開路由：`flora.rsg.com.tw` → 主機本機 `http://127.0.0.1:80`
- DNS：原 A `157.180.85.189`，改成 CNAME `95b30267-cd50-4838-bc90-311778c4e00d.cfargotunnel.com`；Proxy 維持開啟，TTL 自動。
- `cloudflared` 2026.9.1，官方 image 固定 digest：`sha256:b269e8abd07a5bf6f3f4be65d5050b2174eca89c56a0241a8ff32a16aec454e4`。
- 常駐設定：`/root/flora-tunnel/compose.yaml`；Docker restart policy `unless-stopped`，RAM 上限 256 MiB、CPU 上限 0.5、唯讀檔案系統、非 root UID、移除 capabilities。
- 最終參數包含 `--edge-ip-version 4 --region us`；4 條連線均 ready。最後觀察節點 ewr01、ord14、iad21、ord16。
- 維持現有 Cloudflare 訪客 HTTPS 與代理；Cloudflare↔Hetzner 改為加密 Tunnel。主機仍在 Helsinki，路由經美國節點，資料庫沒有遷移。

預設全球路由與只指定 IPv4 的測試仍偶發逾時；指定官方支援的 `us` 路由後，兩個入口及瀏覽器測試均恢復正常。因此最終採用美國路由。這是已驗證的繞路修復，不代表已取得 Cloudflare／上游業者對底層故障的正式根因確認。[官方參數說明](https://developers.cloudflare.com/tunnel/reference/run-parameters/#region)
